# RTX 5090（Blackwell sm_120）配置与调优

本文只讨论单卡 RTX 5090 32GB。所有显存数字都是**估算**（除非标注"外部报告"），用于规划；实际值以 `moss-lora-bench` 为准。

---

## 1. 硬件与软件基线

| 项 | 值 | 说明 |
| --- | --- | --- |
| GPU | GeForce RTX 5090 | GB202，170 SM，21760 CUDA cores，680 第五代 Tensor Cores |
| Compute capability | **12.0（sm_120）** | 旧 wheel 没有对应 kernel |
| 显存 | 32GB GDDR7，512-bit，1792GB/s | 训练时可用约 31GiB（驱动/显示占用） |
| bf16 tensor（FP32 累加） | 209.5 TFLOPS 稠密 / 419 稀疏 | 本项目默认精度 |
| FP8 tensor（FP16 累加） | 419 TFLOPS 稠密 / 838 稀疏 | 默认不用 |
| FP4 tensor | 1676 TFLOPS 稠密 / 3352 稀疏 | 默认不用 |
| 非 tensor FP32 | 104.8 TFLOPS | 参考 |
| 驱动 | ≥ 570.26（Linux） | CUDA 12.8 的最低驱动 |
| Python | 3.10–3.14 | 3.14 需 torch ≥2.9 的 cp314 wheel |
| PyTorch | 2.9.x + cu128 | 项目基线；更新的 cu128/cu130 也可尝试 |

数据来源：[NVIDIA RTX Blackwell GPU Architecture 白皮书](https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf) 附录 A；显存/带宽同时见 [GeForce RTX 50 系列规格](https://en.wikipedia.org/wiki/GeForce_RTX_50_series)。

> 5090 的 bf16 峰值低于 A100 80GB SXM（312 TFLOPS），1792GB/s 带宽也低于 A100 HBM（80GB SXM 为 2039GB/s）。它的优势是 32GB、FP4、成本和单卡可得性。不要用"5090 一定比 A100 快"作为容量规划的前提。

## 2. 安装与验证

### 2.1 驱动

```bash
nvidia-smi
```

右上角 `CUDA Version` 必须 ≥ 12.8。注意这只是**驱动支持的 CUDA 版本**，不是已安装的 toolkit；pip wheel 自带 CUDA runtime，不需要单独装 CUDA toolkit。

如果驱动过旧：

```bash
# Ubuntu 示例；按发行版调整
sudo ubuntu-drivers autoinstall
# 或从 NVIDIA 官网安装 >= 570.26 的驱动
sudo reboot
```

WSL2：在 **Windows 侧**安装带 WSL 支持的 NVIDIA 驱动；不要在 WSL 内安装 Linux 显卡驱动。`nvidia-smi` 在 WSL 内应能正常显示 5090。

### 2.2 PyTorch wheel

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -U pip

pip install torch==2.9.1 --index-url https://download.pytorch.org/whl/cu128
pip install -e .
```

为什么指定 `--index-url`：默认 PyPI 的 Linux wheel 可能是 cu126 或其他 CUDA 版本，不带 sm_120 kernel。cu128 是支持 Blackwell 的最低稳定线；cu129/cu130 也可用，但本项目以 cu128 + torch 2.9 为基线。

### 2.3 验证清单

```bash
python - <<'PY'
import torch

print("torch       :", torch.__version__)
print("cuda build  :", torch.version.cuda)
print("available   :", torch.cuda.is_available())
print("device      :", torch.cuda.get_device_name(0))
print("capability  :", torch.cuda.get_device_capability(0))
print("arch list   :", torch.cuda.get_arch_list())
print("bf16 support:", torch.cuda.is_bf16_supported())

x = torch.randn(4096, 4096, device="cuda", dtype=torch.bfloat16)
y = x @ x
print("bf16 matmul :", y.dtype, float(y.float().abs().mean()))
PY
```

期望：

- `torch.version.cuda == "12.8"`
- `capability == (12, 0)`
- `arch list` 包含 `sm_120`（可能显示为 `sm_120` 或 `sm_120a`）
- bf16 matmul 不报错

### 2.4 常见 wheel 坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `no kernel image is available for execution on the device` | wheel 不含 sm_120 kernel | 重装 cu128+ wheel；不要用 cu118/cu126 |
| `torch.cuda.is_available()` 为 False | 驱动太旧 / WSL 驱动未装 / 容器没传 GPU | 检查 `nvidia-smi`；容器加 `--gpus all` |
| capability 是 `(12, 0)` 但 arch list 没有 sm_120 | 装到了错误构建 | `pip show torch` 看版本；用官方 index 重装 |
| `undefined symbol` / `libcudart.so` 找不到 | 混装了多个 torch（conda + pip） | 干净 venv；`pip uninstall torch` 后重装 |
| `flash-attn` 编译失败 | 预编译轮子不支持 sm_120，源码编译需要完整 CUDA toolkit | **不需要 flash-attn**；用 PyTorch SDPA |
| `torch.compile` 报 Triton/arch 错误 | Triton 版本不认 sm_120 | 升级到 torch 2.9+ 自带 Triton；仍失败则关闭 compile |
| `bitsandbytes` 报错 | 不是本项目依赖 | 不需要安装；fused AdamW 用 PyTorch 原生实现 |

## 3. 显存规划（32GB）

固定成本（与分辨率无关，估算）：

```
DiT bf16                 10.16GB
LoRA r32 fp32 参数        0.30GB
LoRA 梯度                 0.30GB
AdamW m/v                 0.59GB
CUDA context / workspace  1.0–2.0GB
------------------------------------
小计                     ~12.4–13.4GB
```

因此可用于激活的预算约 **18–19GB**。1M 像素不 checkpoint 的激活约 20–23GB；加上权重、优化器状态与 CUDA context，总峰值约 **33–36GB**（见 3.1 表），会超。checkpointing 后激活约 1.5–2.5GB，余量充足。

### 3.1 规划表（估算）

| 分辨率 | batch | checkpointing | compile | 估算峰值 | 相对 step 时间 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| 512² | 1 | 关 | 关 | ~19–21GB | 1.0×（基准） | 最快迭代 |
| 512² | 1 | 开 | 关 | ~13–14GB | ~1.3× | 省显存 |
| 512² | 4 | 开 | 关 | ~15–17GB | ~4×（4 图） | 推荐批量配置 |
| 512² | 4 | 关 | 关 | ~39–41GB | — | **OOM** |
| 512² | 8 | 开 | 关 | ~17–20GB | ~8×（8 图） | 需要同 bucket 样本 |
| 768² | 1 | 关 | 关 | ~25–27GB | ~1.8× | 接近上限 |
| 768² | 1 | 开 | 关 | ~14–15GB | ~2.3× | 稳妥 |
| 1024² | 1 | 开 | 关 | ~14–16GB | ~3.8× | **主配置** |
| 1024² | 1 | 关 | 关 | ~33–36GB | — | **OOM** |
| 1024² | 2 | 开 | 关 | ~16–18GB | ~7.5×（2 图） | 可试；注意碎片 |
| 1536² | 1 | 开 | 关 | ~18–21GB | ~10× | 文字/细节增强 |
| 1536² | 2 | 开 | 关 | ~24–28GB | ~20× | 很紧，不建议 |
| 1024² | 1 | 开 | 开 | +0.5–1.5GB | 0.7–0.9×（估算） | 先跑 bench |

"相对 step 时间"是解析估算的相对值，不是实测。1024² batch 1 checkpointing 的绝对估算约 2.8–3.9s/step（25–35% MFU）。一次 20-step smoke 实测为 1.25s/step（见 §3.3），说明这里的解析值偏保守；不要把估算当作性能预测。

### 3.3 已测：20-step smoke（2026-10-18）

这是一次**真实模型的冒烟测试**，不是长跑或多配置 benchmark。只有 1 个 seed、16 张图、20 个 optimizer step、compile 关闭；不要把它当作收敛质量或稳定吞吐的结论。

| 项 | 实测值 |
| --- | --- |
| 主机 / 环境 | 本地 WSL2 机器；Ubuntu（WSL2） |
| GPU | RTX 5090 32GB（`nvidia-smi` 32607 MiB） |
| 驱动 / PyTorch | 610.57.01 / `torch 2.14.1+cu130` |
| 主机内存 / 磁盘 | 47GiB RAM / 604GB free |
| 数据 | 16 张图，1M 像素（`--target-area 1048576`），`--max-text-length 2048`，fp32 latents |
| 缓存 | 55MB，33.7s wall |
| 训练 | rank 32，bf16，batch 1，gradient checkpointing on，compile off，20 steps |
| step time | **1.25 s/step** steady（前 2 步含 warmup，首次 2.59s） |
| 峰值显存 | **12.84GB** |
| loss | mean 0.423（20 步，仅参考趋势） |
| 训练总墙钟 | 46.6s |
| 采样 | 1024×1024，8 steps，CFG 3，shift 5，skip 22；PNG 656,815 bytes；44s（含模型加载） |

结论边界：

- 1.25s/step 低于 §3.1 的解析估算（2.8–3.9s/step），说明解析模型偏保守；可能是 cu130 kernel、真实 MFU 高于假设、或 20 步短跑尚未进入稳定热状态。**不要**用单次 smoke 外推 2000 步的总时长。
- 采样只跑了 8 步，用于验证链路，不代表官方 50 步的画质。
- 没有测 compile、不同分辨率、batch>1、长步数或显存碎片场景。

WSL2 注意：这次 smoke 期间遇到 `CUDA driver error: unknown error`（发生在 AdamW `_init_group`），`dmesg` 显示 `dxg get_unused_fd_flags failed ... EMFILE`。原因是 WSL 默认 soft `RLIMIT_NOFILE=1024`，GPU 初始化/优化器建组时 fd 耗尽。每次 GPU 运行前执行 `ulimit -n 65536` 即可。详见 §7。

## 4. OOM 阶梯

按顺序尝试，每一步只改一个变量：

1. **确认没有残留进程**：`nvidia-smi`；上次训练异常退出可能留下 context。
2. **batch 降到 1**（512 下 4 → 2）。
3. **打开 gradient checkpointing**：1M 必须；512 大 batch 也建议。
4. **降分辨率**：1024 → 768 → 512。注意缓存与分辨率绑定，需要重建。
5. **缩短文本**：`max-text-length` 512 → 256，重建缓存。layout 数据不要轻易降。
6. **关闭 compile**：`reduce-overhead` 的 CUDA Graphs 会额外占显存；先设 `compile: false`。
7. **设置 allocator**：

   ```bash
   export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
   ```

   必须在进程启动前设置。PyTorch 2.9 使用该变量名；如果未来版本提示改用 `PYTORCH_ALLOC_CONF`，按提示切换。

8. **减少 dataloader / pin memory**：`num_workers: 0`、`pin_memory: false` 只影响 host 内存，不解决 GPU OOM，但能排除 pinned 内存泄漏。
9. **确认没有把 TE/VAE 加载进训练进程**：训练阶段只需要 `transformer/`；缓存阶段的 16.79GB 文本编码器不应存在于训练进程。
10. **仍 OOM**：用 `moss-lora-bench --height 512 --batch-size 1` 建立最小可运行点，再逐项加回。

不要用 `torch.cuda.empty_cache()` 作为常规修复；它只归还缓存，不解决真实的张量占用。

## 5. 性能开关

### 5.1 SDPA backend

```yaml
train:
  sdpa_backend: auto
```

可选值：`auto` / `flash` / `efficient` / `cudnn` / `math`。建议：

- 默认 `auto`；PyTorch 会选择可用后端。
- 显式对比 `flash` 与 `cudnn`：不同序列长度/head 数下最优后端可能不同。
- `math` 仅用于排查数值问题，速度明显更慢。
- 本项目 head_dim=128，满足 flash 的常见约束；mask 是 padding mask，不是 causal mask。

### 5.2 torch.compile

```yaml
train:
  compile: true
  compile_mode: default
```

- 实现默认 `dynamic=True`：文本长度逐 batch 变化，静态 shape 会导致反复重编译。
- `default` 最稳；`max-autotune` 编译很久、可能占更多显存；`reduce-overhead` 使用 CUDA Graphs，对动态输入不友好。
- 第一次 step 可能几十秒到几分钟；之后的收益常见在 10–30%（估算，视 kernel 而定）。
- 编译缓存默认在 `~/.cache/torch/inductor` 或 `TORCHINDUCTOR_CACHE_DIR`；SSD 上更快。
- 如果 compile 报错或 OOM，直接关掉；它不是正确性的一部分。

### 5.3 checkpointing

```yaml
train:
  gradient_checkpointing: true
```

- 省的是激活，不是权重。
- 代价是多一次前向（训练 FLOPs 从 3× 变 4× 前向，约 +33%）。
- 1M 必开；512 下 batch ≥4 建议开；512 batch 1 可以关掉换速度。

### 5.4 Dataloader

```yaml
data:
  num_workers: 4
  pin_memory: true
```

- latent 已缓存，worker 只做文件读取、resize/crop（缓存阶段已完成）、collate；4–8 足够。
- Windows/WSL 下多 worker 可能更慢；先试 0/2/4。
- `pin_memory` 对小块 latent 收益有限，但配合非阻塞拷贝通常有益。
- 缓存文件放在本地 NVMe；网络盘会拖慢第一个 epoch。

### 5.5 避免 TE 与 DiT 共存

- 缓存：先编码文本（TE 上 GPU），释放后再加载 VAE；不要同时保留。
- 训练：不加载 TE/VAE。
- 采样：TE 只用于 encode prompt，随后 offload 到 CPU，再加载 DiT/VAE。
- 验证采样：训练进程内触发时应使用缓存中的 prompt embedding，**不要**重新加载 TE；独立的 `moss-lora-sample` 进程按 TE → 卸载 → DiT/VAE 的顺序执行。

## 6. 相对收益（解析，非实测）

| 手段 | 相对收益（估算） | 成本 |
| --- | --- | --- |
| 离线缓存 vs 每步跑 TE+VAE | 训练 step 不再包含 8.4B TE 前向；显存少 17GB 量级 | 一次性预处理；磁盘 2–6MB/图 |
| bf16 vs fp32 基座 | 权重减半；tensor core 吞吐更高 | 无（与官方推理一致） |
| SDPA 融合 attention vs math | attention 部分显著加速；避免 S×S 物化 | 后端/形状限制 |
| checkpointing | 激活降约 85–90% | 计算 +33% |
| compile | step 时间 -10–30% | 编译时间；动态形状复杂度 |
| fused AdamW | optimizer step 开销下降 | 仅 CUDA |
| bucket sampler | 消除 padding token 浪费；aspect 多样时收益明显 | 需要同 bucket 样本 |
| EMA | 质量更稳 | +0.3GB，每步更新 |

这些比例受实现和形状影响很大，**不要**把它们当作可叠加的乘法。用 bench 逐项测。

## 7. Windows / WSL2 补充

- 推荐 WSL2 + Ubuntu 22.04/24.04；Windows 原生未被项目验证。
- Windows 侧安装 NVIDIA 驱动（含 WSL 支持），WSL 内不要重复安装驱动。
- WSL 的显存由 Windows 驱动管理；`nvidia-smi` 可用，但显存上限可能略低于 32GB（桌面占用）。
- 文件 I/O：把数据集和缓存放在 WSL 的 ext4 文件系统（`~/...`），不要放在 `/mnt/c/...`；后者对大量小文件很慢。
- `torch.compile` 在 WSL 下可用，但首次编译更慢；遇到 Triton 问题先关闭。
- 多 worker dataloader 在 WSL 下可能受 `/dev/shm` 限制；必要时 `num_workers: 0`。
- **`EMFILE` / `CUDA driver error: unknown error`**：WSL 的 soft `RLIMIT_NOFILE` 默认是 1024。GPU 初始化、DataLoader worker、AdamW `_init_group` 等会快速耗尽 fd，典型现象是训练刚开始就报 `CUDA driver error: unknown error`，而 `dmesg` 里有 `dxg get_unused_fd_flags failed ... EMFILE`。每次 GPU 运行前执行：

  ```bash
  ulimit -n 65536
  ```

  再启动训练/采样。写进 `~/.bashrc` 只对交互 shell 生效；CI/远程命令要显式带上。不要把这个错误误判为驱动或显存问题。

## 8. 快速自检脚本

```bash
python - <<'PY'
import torch, time

assert torch.cuda.is_available()
assert torch.cuda.get_device_capability(0) == (12, 0), "not sm_120"
assert torch.cuda.is_bf16_supported()

x = torch.randn(8192, 3072, device="cuda", dtype=torch.bfloat16)
w = torch.randn(3072, 3072, device="cuda", dtype=torch.bfloat16)
for _ in range(3):
    y = x @ w
torch.cuda.synchronize()

t0 = time.time()
for _ in range(20):
    y = x @ w
torch.cuda.synchronize()
dt = (time.time() - t0) / 20
flops = 2 * 8192 * 3072 * 3072
print(f"bf16 GEMM: {flops / dt / 1e12:.1f} TFLOPS, {dt*1e3:.2f} ms")
print(f"peak allocated: {torch.cuda.max_memory_allocated()/2**30:.1f} GiB")
PY
```

这个微基准只验证"bf16 tensor core 能用"，不代表 DiT 的实际 MFU。GEMM 效率通常高于整模型训练。
